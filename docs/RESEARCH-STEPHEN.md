# Give Stephen verbs, not a mouse

Build Stephen as a small set of **allowlisted, high-level desktop verbs** added to browser-hub: open an approved app, open an approved URL in Zen or Chrome, report the frontmost app, and hand off to browser-hub's existing gated tools for anything inside a page. Do not expose raw mouse, keyboard and screenshot control. "Open YouTube" is one deterministic `open` call. A computer-use loop costs about **4,500 tokens of tool definition plus 1,000–1,800 per screenshot**, Anthropic calls it potentially "too slow" for interactive use, and it puts every pixel on screen in front of the model, which is the main prompt-injection channel. Keeping screenshots out of the MVP is the strongest single "can't do anything stupid" control available. The voice front end should run entirely on the Mac. A Swift menu-bar app owns the microphone, a listening indicator and a stop hotkey. **sherpa-onnx keyword spotting** detects "HEY STEPHEN" from a text keywords file with no training; Picovoice Porcupine is out because its free tier was shut off on 30 June 2026. **Silero VAD plus whisper.cpp** (or Apple's SpeechAnalyzer on macOS 26) transcribes the command. The **Claude Agent SDK in streaming-input mode** hands the transcript to one long-lived Claude session with browser-hub attached, and `say` speaks the reply. Two constraints shape the plan. The Agent SDK must run on a Console **API key**, because Anthropic does not let SDK-built products use claude.ai subscription logins without approval. And every macOS permission lands on whichever app macOS deems "responsible", so the Swift app should be that app from day one. If the MVP stays with open-verbs, the only grants it needs are **Microphone** and, for a consumed stop key, **Input Monitoring**. Accessibility and Screen Recording wait until a GUI fallback is turned on deliberately.

## "Open YouTube" is a one-line `open` call, not a computer-use loop

The leading desktop agents now share one rule: use the most specific interface that exists and touch pixels last. Claude Code's own ordering is an MCP server for the service first, then Bash, then Claude in Chrome, and screen control only after those. Its docs explain that "computer use is the broadest and slowest, so Claude tries the most precise tool first" ([Claude Code docs](https://code.claude.com/docs/en/computer-use.md)). Microsoft's UFO² reaches the same conclusion on Windows. Its "Puppeteer" component prefers native APIs such as a direct `save_as()` over dialog clicks, and speculative batching **cut steps by up to 51.5%** ([alphaXiv UFO²](https://alphaxiv.org/overview/2504.14603v2)). Peekaboo, the most active open-source macOS tool, recommends semantic actions like `menu click` over coordinates ([GitHub openclaw/Peekaboo](https://github.com/openclaw/Peekaboo)).

The cost data shows why this matters for a voice assistant. Anthropic's current computer-use toolset costs **about 4,500 input tokens to define**, each screenshot adds **roughly 1,000–1,800 tokens**, and "long loops accumulate these quickly". Anthropic warns that latency "might be too slow compared to regular human-directed computer actions" ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/computer-use)). A PCWorld tester used up most of a five-hour Pro allotment in about 30 minutes of Claude driving a Mac. The same session stalled indefinitely on the Chess app's 3D board while tokens drained ([PCWorld](https://www.pcworld.com/article/3097542/claude-controlled-my-mac-for-half-an-hour-it-was-a-wild-worrisome-ride.html)). A user who says "Hey Stephen, open YouTube" expects a result in a second or two. A screenshot-verify loop cannot deliver that. An `open` call followed by a cheap check that the target app is now frontmost can, and it adds roughly zero tokens.

Safety points the same way. In the independent RedTeamCUA benchmark (ICLR 2026), raw computer-use agents carried out injected high-risk tasks end to end at high rates: **Claude Opus 4.5 CUA 83%**, Sonnet 4.5 60%, and Operator with its confirmation checks 10% ([arXiv 2505.21936v5](https://arxiv.org/html/2505.21936v5)). Anthropic's much lower published figures, such as the Opus 5 browser agent at **0% across 129 scenarios with Auto Mode** and 3.7% without it, are browser measurements with product classifiers attached, and no Claude 5-series computer-use figures have been published ([The Decoder](https://the-decoder.com/opus-5-may-have-solved-browser-based-prompt-injection-the-biggest-security-flaw-haunting-ai-agents/)). Real attacks have come through the screen. A hidden web instruction got Claude computer use to download, `chmod` and run a botnet binary (ZombAIs) ([Simon Willison](https://simonwillison.net/2024/Oct/25/zombais/)). At 39C3, a fake "Are you a computer?" dialog got an agent to paste and run a clipboard command (ClickFix) ([heise](https://heise.de/-11125687)). If Stephen's desktop tools never capture the screen or read on-screen text, those attack paths do not exist for it.

Two routes to "borrow" Anthropic's computer use are closed anyway. The built-in `computer-use` MCP server in Claude Code works **only in interactive sessions, not `-p`**, needs a Pro or Max plan, and is a research preview ([Claude Code docs](https://code.claude.com/docs/en/computer-use)). A headless voice daemon cannot use it. The API's `computer_toolset_20260801` works purely on pixel coordinates and has no accessibility-tree or "open app" primitive ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/computer-use)). It offers the broadest capability with the least structure, which is the wrong trade for a small feature.

Routing follows from this. A bare "open YouTube" should not attach browser-hub at all. `open -a Zen https://www.youtube.com` (or Chrome) launches or focuses the browser without Zen's debugging-port relaunch or Chrome's per-connection Allow dialog. browser-hub's in-page tools come in only for follow-ups such as "play the first lo-fi result", and their existing origin scope, sensitive-field firewall and elicitation gate apply unchanged. The table lists the proposed desktop surface. The tiers mirror Claude Desktop's fixed categories, where "browsers and trading platforms are view-only, terminals and IDEs are click-only, and everything else gets full control" ([Claude Code docs](https://code.claude.com/docs/en/computer-use.md)), but Stephen is stricter: terminals are never reachable.

| Tool | MVP? | Implementation | Gate in code |
|---|---|---|---|
| `open_app(name)` | Yes | `open -b <bundleId>` from an allowlist that maps spoken names to bundle IDs | Allowlist only; no confirmation (reversible) |
| `open_url(url, browser?)` | Yes | `open -a Zen <url>` or `open -a "Google Chrome" <url>` | `https:` only, eTLD+1 allowlist (youtube.com, etc.); off-list asks for confirmation; rejects `file:`, `javascript:`, custom schemes, `.app/.pkg/.command/.sh` |
| `desktop_status` | Yes | Frontmost bundle ID (NSWorkspace), screen-locked flag, secure-input flag | Read-only |
| browser-hub tools | Yes (existing) | Unchanged | Existing policy engine and elicitation |
| `ui_snapshot` / `ui_press` / `ui_type` | No, off by default | Peekaboo CLI subprocess, AX element IDs | Full-tier allowlist, frontmost check, secure-input refusal, confirmation |
| `screenshot`, raw `click(x,y)`, key chords | Not exposed | n/a | n/a |

## Reuse Peekaboo's plumbing and Anthropic's UX; build the gate yourself

No project surveyed offers "safe by construction" desktop control. The reusable pieces are plumbing and design patterns. The safety layer has to be Stephen's own.

| Project | What it is (Oct 2026) | Verdict for Stephen |
|---|---|---|
| **Peekaboo** (openclaw, formerly steipete) | MIT Swift CLI plus MCP. Accessibility (AX) tree with opaque element IDs, plus screenshots. macOS 15+, `npx -y @steipete/peekaboo`. Window-ID pinning; `--allow-foreground` consent for targetless chords. **No allowlist or confirmation feature** ([GitHub](https://github.com/openclaw/Peekaboo)) | **Reuse as a subprocess** for the v2 GUI fallback, called only from Stephen's gated tools. Never register its MCP server with Claude directly, because that bypasses the gate |
| **macos-automator-mcp** (steipete) | MIT. `execute_script` runs arbitrary AppleScript/JXA "with the privileges of the process hosting the MCP server" ([GitHub](https://github.com/steipete/macos-automator-mcp)) | **Do not expose**; arbitrary AppleScript is shell access. Its bundled snippets are useful references for hard-coded helpers |
| **mcp-server-macos-use** (mediar-ai) | Swift. Open app, click, type, key by PID; re-reads the AX tree after each action instead of screenshotting. License listed as NOASSERTION ([mcp.so](https://mcp.so/servers/mcp-server-macos-use?tab=tools)) | Copy the verification idea; avoid the dependency until the license is clear |
| **Terminator** (mediar-ai) | MIT. Deterministic AX workflows, AI only for recovery. Feature table says **Windows only** ([GitHub](https://github.com/mediar-ai/terminator)) | Not usable on macOS |
| **cua** (trycua) | MIT core with some FSL/AGPL parts. Lume macOS VMs (~50 GB image), Cua Driver MCP. "Does not solve agent brittleness or misclicks" ([andrew.ooo](https://andrew.ooo/posts/trycua-cua-open-source-computer-use-agents/); [Simular, competitor-authored](https://platform.simular.ai/compare/open-source-computer-use-agents)) | Too heavy for the real desktop; useful as a test sandbox |
| **Agent S / UFO / open-interpreter** | Agent S: Apache-2.0, cross-platform, needs a separate grounding model. UFO: Windows and Linux. open-interpreter has pivoted to coding ([Simular comparison](https://platform.simular.ai/compare/open-source-computer-use-agents)) | Not a fit |
| **Claude Code / Desktop computer use** | Product feature. Per-app approval, tiers, consumed Esc, lock file, hidden apps ([Claude Code docs](https://code.claude.com/docs/en/computer-use.md)) | **Copy its safety UX**; you cannot embed it |

The build-versus-reuse line is clear. The MVP verbs are about a hundred lines of TypeScript around `/usr/bin/open` and a status query, so build them inside browser-hub, which already has an MCP layer, a policy engine and an audit log. Reuse Peekaboo only when a real need appears for native-app GUI control, such as "click Play in Music". Even then, wrap its CLI so every call passes Stephen's allowlist, frontmost check and confirmation first.

## Every macOS grant lands on whichever app is "responsible"

macOS splits desktop control into separate privacy (TCC) grants, and it charges each one to the **responsible app** rather than to the process that makes the call. Claude Code's CLI shows this. To fix a repeating Screen Recording prompt, its docs tell users to confirm "**your terminal app** is listed and enabled", and they warn that a restart may be needed after granting ([Claude Code docs](https://code.claude.com/docs/en/computer-use)). Apple's DTS engineers point to the concept of "responsible code" but decline to document the algorithm, calling it "complex and subject to change" ([Apple Forums 741622](https://developer.apple.com/forums/thread/741622)). So if browser-hub runs as a stdio child of Claude Code under iTerm, any Accessibility grant goes to iTerm, and every other program run from iTerm gets the same power. If browser-hub is instead spawned by Claude Desktop, the grant goes to a different app and the earlier grant does not apply.

| Grant | Needed for | Stephen MVP? |
|---|---|---|
| **Microphone** | Wake word and STT capture | Yes |
| **Input Monitoring** | A CGEventTap that sees and *consumes* a global stop key ([Apple Forums 707680](https://origin-devforums.apple.com/forums/thread/707680)); an active tap may also need Accessibility (unverified) | Yes, for the stop key |
| **Accessibility** | Posting synthetic mouse and key events (CGEvent), reading the AX tree, `AXPress` | No; only when the GUI fallback is on |
| **Screen Recording** | Any screenshot (ScreenCaptureKit or `screencapture`) | No |
| **Automation** | AppleScript `tell application "System Events"` | Avoid entirely |

`open`, NSWorkspace's frontmost-app query and the lock and secure-input checks need none of these grants. That is why the open-verbs MVP is cheap to set up as well as safe.

The design consequence is to make the Swift menu-bar app the responsible process for everything. It captures audio, so it owns Microphone. It hosts the event tap, so it owns Input Monitoring. If it launches the Node daemon (which runs the Agent SDK, which spawns browser-hub), the grants probably attribute to "Stephen" instead of a terminal. This attribution is inferred from the responsible-code model and needs a day-one test, because Apple does not document it. Peekaboo uses the same pattern: a signed menu-bar app handles "permission onboarding" while the CLI and MCP install from npm or brew ([GitHub openclaw/Peekaboo](https://github.com/openclaw/Peekaboo)). One unverified but widely reported caveat matters here. TCC ties a grant to the binary's code-signing requirement, so an ad-hoc-signed rebuild can silently lose its grants while System Settings still shows them on. Sign every build with one consistent certificate and keep the bundle ID fixed; `tccutil reset` clears a broken entry.

When the GUI fallback is eventually turned on, four platform facts apply.

The Node native-module route is mostly closed. **nut.js pulled its prebuilt packages from public npm in April 2024** ([nut.js #587](https://github.com/nut-tree/nut.js/issues/587)), and its image-matching plugin became paid at $40/month ([nutjs.dev](https://nutjs.dev/blog/money)). @jitsi/robotjs exists, but its arm64 status was not verified ([socket.dev](https://socket.dev/npm/package/@jitsi/robotjs/overview/0.6.23)). Calling Peekaboo, or a small Swift helper that calls CGEvent and AX directly, avoids N-API rebuilds entirely.

Building against the macOS 15 SDK turns `CGWindowListCreateImage` into a hard error: "**obsoleted in macOS 15.0** – Please use ScreenCaptureKit instead" ([eclipsa-audio-plugin #10](https://github.com/google/eclipsa-audio-plugin/issues/10)). Any capture code has to use ScreenCaptureKit or shell out to `screencapture`.

Screen Recording comes back for confirmation. Sequoia moved from a planned weekly prompt to a **monthly "Continue to Allow" dialog** that also hits ScreenCaptureKit apps ([9to5Mac](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/); [TidBITS](https://tidbits.com/2024/09/23/how-to-avoid-sequoias-repetitive-screen-recording-permissions-prompts/)). Whether macOS 26 Tahoe changed this is unknown. An always-available assistant would hit that dialog at the moment of use, so it should check access first and say so aloud rather than fail silently.

Retina scaling causes misclicks. Claude Code downscales a 3456×2234 capture to about 1372×887 ([Claude Code docs](https://code.claude.com/docs/en/computer-use)), and Anthropic warns that without downscaling or halving coordinates, Retina clicks land 2× off ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/computer-use)). Acting on AX element IDs instead of model-estimated pixels removes this error class wherever an AX tree exists. That covers native AppKit and SwiftUI apps well, Chromium and Electron apps only lazily, and games and canvases not at all.

## Safety lives in deterministic code below the model

Every vendor says prompt injection is unsolved. Anthropic says "in some circumstances, Claude follows commands found in content even when they conflict with your instructions" ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/computer-use)), and calls even a 1% attack success rate "meaningful risk" ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). Rehberger's 39C3 conclusion is the operating principle: treat the model as untrusted, and put security controls "downstream of the LLM output" ([heise](https://heise.de/-11125687)). browser-hub's policy engine already does this for web pages. Stephen adds the desktop and voice layers below, each taken from a shipped precedent.

**Allowlist, then hard-deny.** Only bundle IDs on Stephen's list can be opened. Hard-coded denials cover the apps Anthropic flags as sentinels: terminals and IDEs ("Equivalent to shell access"), Finder ("Can read or write any file") and System Settings ([Claude Code docs](https://code.claude.com/docs/en/computer-use.md)). Add Keychain Access, Script Editor, Automator, Shortcuts, password managers, and the "investment and trading platforms, cryptocurrency" category that Claude Desktop blocks by default ([Claude support](https://support.claude.com/en/articles/14128542-computer-use-safety)). The URL-scheme filter matters as much as the app list. Without it, `open` turns into code execution, which is exactly the download-and-run and ClickFix pattern.

**Never touch the security plane.** At 39C3, injected agents flipped their own auto-approve setting and registered malicious MCP servers ([heise](https://heise.de/-11125687)). No published incident shows an agent clicking "Allow" on a macOS TCC prompt, but the same class of attack applies. Stephen's tools should refuse any action whose target is System Settings, SecurityAgent, UserNotificationCenter or a Gatekeeper dialog. Stephen's allowlist and config files must not be writable through any tool, and TCC grants stay a one-time manual step at install.

**OS-state preconditions, checked before every action.** Refuse everything when the screen is locked. Before any typed input, confirm the frontmost bundle ID still matches the app the action was scoped to. Peekaboo requires a fresh snapshot for window-targeted chords for the same reason, because keystrokes landing in the wrong window is a known hazard ([GitHub openclaw/Peekaboo](https://github.com/openclaw/Peekaboo)). Refuse to type at all while Secure Input is on, which Chromium and WebKit enable for password fields ([Chromium](https://chromium.googlesource.com/chromium/src/+/d4afc97b7/ui/base/cocoa/secure_password_input.mm); [Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/determine-if-the-system-is-in-secure-input-mode/858)). Then say "you'll need to type that one yourself". This mirrors Operator's takeover mode, where the agent "does not collect or screenshot what the user enters" ([OpenAI](https://openai.com/index/introducing-operator/)).

**Confirmation classified in code, not by the model.** Opening an allowlisted app or URL is reversible and needs no confirmation. Anything that sends, buys, deletes, posts, grants or leaves the allowlist does. Confirmations are the best-measured control. In Operator's system card they "reduced the risk of model mistakes by roughly 90%" ([Operator system card](https://cdn.openai.com/operator_system_card.pdf)), and in RedTeamCUA they cut attack success by **58.62%** relative to running without them ([arXiv 2505.21936v5](https://arxiv.org/html/2505.21936v5)).

Voice adds a twist the published research does not cover. Stephen's own actions start audio: it opens YouTube, and YouTube talks. A video, podcast or call that says "Hey Stephen, …", or "yes" at the wrong moment, is an audio prompt injection. "Stephen" is also a common name with a homophone, "Steven", so collisions in ordinary conversation will happen. This threat is our own inference, not a sourced finding. The mitigations are cheap. Suspend wake detection while Stephen's TTS is speaking. Raise the keyword threshold, or require push-to-talk, while media is playing. Accept spoken "yes" only for low-risk confirmations, and require a physical confirmation (a click on a native dialog or a key press) for anything high-risk.

**A stop channel injection cannot press.** Copy Claude Code's design: a visible "is using your computer · press Esc to stop" notice, and an Esc that aborts "from anywhere" and is "consumed so prompt injection can't use it to dismiss dialogs" ([Claude Code docs](https://code.claude.com/docs/en/computer-use)). Claude Desktop adds a red glowing screen border ([PCWorld](https://www.pcworld.com/article/3097542/claude-controlled-my-mac-for-half-an-hour-it-was-a-wild-worrisome-ride.html)). In Stephen, the stop hotkey and a spoken "Stephen, stop" both call the Agent SDK's `interrupt()`, which ends a turn cleanly. The CLI's SIGTERM, by contrast, leaves the turn unfinished ([Claude Code headless](https://code.claude.com/docs/en/headless)). Once raw input exists, add a pyautogui-style check: abort if the cursor is in a screen corner or has moved since Stephen last placed it.

**Bound the blast radius.** Keep a single-controller lock file, as Claude Code does. Cap each command with the SDK's `maxTurns` and `maxBudgetUsd` ([Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)). No source gives recommended numbers; something like 6 turns and a few cents per spoken command is a reasonable starting point. Write every tool call to browser-hub's existing append-only audit log. Use `disallowedTools` to remove Bash, Write, Edit and WebFetch from the Claude session, because those rules "hold even in `bypassPermissions`" ([Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)). A voice-triggered agent with shell access turns every false wake into a potential incident.

## A fully local pipeline from "Hey Stephen" to a spoken reply

**Wake word.** The usual answer stopped working this year. Picovoice confirmed that Free Tier AccessKeys stopped working on **30 June 2026**, that "the SDK does not run without a valid key", and that "there is no non-commercial tier planned" ([Home Assistant Community](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744)). Its pricing page now redirects to a sales contact form ([picovoice.ai](https://picovoice.ai/pricing)). **sherpa-onnx open-vocabulary keyword spotting** is the best fit for a Node stack. You write "HEY STEPHEN" into a keywords file, tokenize it with `sherpa-onnx-cli text2token`, and run the 3.3M-parameter GigaSpeech model. Its int8 encoder is 4.6 MB and the whole package about 19 MB, trained on 10k hours of audio. The example settings were `keywords_threshold=0.25` and `keywords_score=1` ([sherpa-onnx KWS models](https://k2-fsa.github.io/sherpa/onnx/kws/pretrained_models/index.html)). A newer December 2025 zh-en model has a chunk-8 variant with **about 160 ms latency**. The Node binding `sherpa-onnx-node` exposes `KeywordSpotter` with keywords fixed at construction ([sherpa-onnx JS API](https://k2-fsa.github.io/sherpa/onnx/javascript-api/examples/api_keyword_spotter.html)). The weakness is that **no false-alarm rates are published** for the English models, so thresholds must be tuned by hand.

The upgrade path is a custom **openWakeWord** "hey_stephen" model trained on synthetic Piper speech in under an hour. It targets **under 5% false rejects and under 0.5 false accepts per hour** ([PyPI openwakeword](https://pypi.org/project/openwakeword)). Two caveats apply. Its last release was **0.6.0 in February 2024**, and its pre-trained models are CC BY-NC-SA, so you would run your own trained model in a Python sidecar. A cheap extra filter is to check that the post-wake transcript starts with "hey stephen" before acting on it.

**Endpointing and speech-to-text.** After the wake word, record until **Silero VAD** detects end of speech. Silero is built into both whisper.cpp and openWakeWord. Then transcribe the clip. **whisper.cpp** (MIT) runs fully on the GPU via Metal and can move the encoder to the Neural Engine via Core ML, which is "more than x3 faster compared with CPU-only". base.en needs 142 MiB on disk and about 388 MB of RAM; small.en needs 466 MiB and about 852 MB ([whisper.cpp README](https://huggingface.co/datasets/echodict/whisper.cpp/blob/main/README.md)). On macOS 26, Apple's **SpeechAnalyzer** runs fully on device with system-managed models and benchmarks **2.2× faster than Whisper Large V3** ([Gigazine](https://www.gigazine.net/gsc_news/en/20250619-apple-speech-analyzer)). It has no JavaScript binding ([addpipe](https://blog.addpipe.com/apple-speechanalyzer-api/)), so it only makes sense inside the Swift app. Since Stephen has a Swift app anyway, SpeechAnalyzer is the low-maintenance default on Tahoe, with whisper.cpp as the cross-version fallback. No published source measures end-to-end latency for either engine on short commands, so benchmark on the target Mac.

**Handing the command to Claude.** The **Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk`) is the right bridge. Passing `query()` an AsyncIterable prompt keeps one session open across commands. That gives continuity ("open YouTube", then "search for lo-fi") and enables `interrupt()`, `streamInput()` and `setModel()`. browser-hub attaches through `mcpServers`, and `settingSources: []` keeps the user's personal Claude Code settings out ([Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)). One integration detail is easy to miss and would break browser-hub's safety gate silently: **if `onElicitation` is omitted, the SDK auto-declines every elicitation**. browser-hub's confirmations would therefore fail closed, and the user would never be asked. Implement `onElicitation` (and `canUseTool`) to route each request to a spoken prompt or a native dialog, following the voice-versus-physical split above.

The per-command CLI alternative, `claude -p --bare --mcp-config … --output-format json --resume <id>`, works for a prototype. But it can wait up to **`MCP_TIMEOUT` (30 s)** for MCP servers on every invocation, and since v2.1.302 `-p` runs start in a Manual mode that denies approval-requiring calls unless a hook or `--permission-prompt-tool` approves them ([Claude Code headless](https://code.claude.com/docs/en/headless)). Either path needs an API key. `--bare` "never reads OAuth credentials", and the SDK docs state that "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). Whether a solo developer running the SDK only for themselves counts as "offering" it is not addressed, so plan on per-token billing with a fast model. The same page sets the branding rule: "Stephen, powered by Claude" is allowed, while anything that resembles Claude Code is not. Separately, steer clear of Marvel's Doctor Strange imagery.

**Text-to-speech.** Ask Claude for a one-sentence spoken summary, which `--json-schema` or a system-prompt instruction can enforce ([Claude Code headless](https://code.claude.com/docs/en/headless)), and speak it with macOS `say` or AVSpeechSynthesizer in the Swift app. Both are free and offline. Piper, the same engine used to synthesize wake-word training data, is the local neural upgrade. No sourced latency or quality comparison was available.

## The MVP: one menu-bar app, one daemon, one gated server

```
Stephen.app (Swift, MenuBarExtra, signed, launch-at-login)
  ├─ owns: Microphone, Input Monitoring, status icon (idle/listening/thinking/acting),
  │        stop hotkey (consumed), native confirm dialogs, SpeechAnalyzer (macOS 26)
  └─ spawns + streams 16 kHz PCM → stephen-daemon (Node/TS)
        ├─ sherpa-onnx-node KWS "HEY STEPHEN" → Silero VAD → STT (whisper.cpp or transcript from app)
        ├─ Claude Agent SDK, streaming-input session, API key, fast model,
        │    maxTurns/maxBudgetUsd, disallowedTools [Bash, Write, Edit, WebFetch…],
        │    onElicitation/canUseTool → voice or dialog confirmation
        └─ mcpServers: browser-hub (stdio)
              ├─ existing: Zen (BiDi) + Chrome (CDP) tools behind policy engine
              └─ new desktop module: open_app, open_url, desktop_status
                   (allowlists, deny list, lock/secure-input/frontmost checks, audit log)
  ← reply text → say / AVSpeechSynthesizer
```

Build it in four steps, each shippable on its own.

**Step 1: desktop module in browser-hub.** Add `open_app`, `open_url` and `desktop_status` behind the existing policy engine and audit log, and test them from Claude Code before any voice work.

**Step 2: voice daemon in Node.** Run it from a terminal at first, accepting the terminal's microphone grant, and wire sherpa-onnx, VAD, whisper.cpp, the Agent SDK session and `say`. Measure false wakes against an hour of YouTube audio and tune `keywordsThreshold`.

**Step 3: move capture into the Swift app.** Move capture, the indicator, the stop hotkey and confirmation dialogs into a consistently signed Stephen.app, confirm that TCC now lists "Stephen" rather than the terminal, and switch STT to SpeechAnalyzer on macOS 26.

**Step 4: GUI fallback, only if needed.** Add it off by default, as Peekaboo-backed `ui_snapshot` and `ui_press` against a short full-control allowlist. That is the first point where Accessibility gets granted. Screenshots stay out unless a specific app with no AX tree demands them, and the monthly Screen Recording re-prompt is a good reason to resist.

## Conclusion

The request sounds like "give Claude my whole Mac", but the evidence points to the opposite design. The feature becomes safer and better at once by narrowing what the model can reach. Each capability Stephen does not have (pixels, raw keys, shell, AppleScript) removes a documented attack and a latency source together, and the useful voice commands ("open X", "play Y", "go back") almost all map to deterministic verbs or browser-hub's existing gated tools. Read browser-hub's growth into Stephen as adding a second front door, voice, to the same policy engine, not as adding a computer-use agent.

The new risks are the ones the research literature has not yet studied. Audio is now an injection channel, and Stephen's own actions start the media that can trigger it. The wake word is a common name. And a missing `onElicitation` handler would quietly turn every safety confirmation into an automatic "no", which looks safe until someone tries to rely on it. Three unknowns deserve a day-one test because no source settles them: whether TCC attributes the Node daemon's actions to Stephen.app, how often sherpa-onnx false-wakes on real household and media audio, and whether macOS 26 still re-prompts monthly for Screen Recording.
