# Build one Puppeteer bridge, two protocols

Build a single local stdio MCP server in Node.js on **puppeteer-core**. It should speak **CDP to Chrome** and **WebDriver BiDi to Zen**, own its page-snapshot and element-reference layer, and enforce safety in code rather than in the prompt. The two browsers need different attach strategies. For Chrome, the only supported way to drive the user's real, logged-in profile is the **Chrome 144+ user-approved "auto-connect" path**. The user turns on remote debugging once at `chrome://inspect/#remote-debugging`, the server reads `DevToolsActivePort` from the default profile, and Chrome shows an Allow dialog for each connection. Since Chrome 136 the classic `--remote-debugging-port` flag is ignored on the default profile. Zen is a Firefox-release fork (Firefox 158.0.1 as of October 2026). Its Remote Agent listens only if the browser was **launched with `--remote-debugging-port`**, so you cannot attach to a Zen the user opened normally. The server must relaunch Zen, either on the real profile after the user quits it, or on a dedicated agent profile that runs alongside. CDP is gone from Firefox, and Puppeteer's accessibility snapshot does not work over BiDi. The practical design is therefore one injected DOM-walker that produces the same compact, ref-tagged, interactive-only tree in both browsers, behind a tool surface modelled on Playwright MCP and chrome-devtools-mcp. Safety is the hard part. Even Anthropic's best published defenses leave an adaptive prompt-injection success rate of about **1–2%**. The server needs origin scoping, sensitive-field blocking, human confirmation for consequential actions that the model cannot forge, and an audit log.

## Chrome's real profile opens only through the 144+ consent dialog

The obvious approach, launching Chrome with `--remote-debugging-port=9222`, no longer works on a user's everyday profile. In March 2025 Google announced that from **Chrome 136**, `--remote-debugging-port` and `--remote-debugging-pipe` "will no longer be respected if attempting to debug the default Chrome data directory." The reason is that infostealers had turned to the debugging port to pull decrypted cookies after App-Bound Encryption shipped. A non-default data directory uses a different encryption key ([Chrome for Developers](https://developer.chrome.com/blog/remote-debugging-port?hl=en)). This rules out the tempting workaround of copying the real profile into a new `--user-data-dir`: the cookies would not decrypt, and the attempt recreates the infostealer pattern.

The supported replacement arrived with **Chrome 144** (announced December 2025). The user opens `chrome://inspect/#remote-debugging` and checks "Allow remote debugging for this browser instance." Chrome then writes a `DevToolsActivePort` file into the default profile root, `~/Library/Application Support/Google/Chrome/` on macOS. Each client connection triggers an **Allow/Deny dialog**, and the "controlled by automated test software" banner shows while a session is active ([Chrome for Developers blog](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session?hl=en); [DevTools auto-connect docs](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect)). The file holds the port on line 1 and the browser target path on line 2. Google's chrome-devtools-mcp 1.12.0 reads both lines itself and connects to `ws://127.0.0.1:${port}${path}`, with a code comment noting it re-implements logic that Puppeteer's `connect({channel:'chrome'})` marks as experimental ([npm chrome-devtools-mcp 1.12.0](https://www.npmjs.com/package/chrome-devtools-mcp/v/1.12.0)). Your server should do the same: read the file, use the full path from line 2, and pass it as `browserWSEndpoint`. Playwright's channel shortcut assumes `/devtools/browser`, and a still-open Playwright issue reports timeouts against inspect-enabled Chrome until the endpoint form was changed ([microsoft/playwright#40027](https://github.com/microsoft/playwright/issues/40027)). A third-party write-up warns that the HTTP discovery endpoints (`/json/version`) may return 404 in this mode, so don't depend on them ([miniasp](https://blog.miniasp.com/post/2026/08/16/chrome-remote-debugging-autoconnect-9222-cdp)). A macOS test on Chrome 147 confirmed that attaching this way lists the open tabs and **reuses the logged-in session** ([Classmethod](https://dev.classmethod.jp/articles/playwright-cli-attach-local-chrome/)).

The per-connection dialog shapes the design. The server should hold **one long-lived connection** and reconnect only when it has to, not reconnect for every tool call. Connect with `defaultViewport: null` so the user's windows are not resized. Use `targetFilter` to ignore extension and service-worker targets, and set `handleDevToolsAsPage` in case the user has DevTools open. These are the options chrome-devtools-mcp passes ([npm chrome-devtools-mcp](https://www.npmjs.com/package/chrome-devtools-mcp/v/1.12.0)). End sessions with `browser.disconnect()`. In Puppeteer, `browser.close()` quits the user's Chrome. Auto-connect binds to the **default profile as Chrome determines it**, with access to all of that profile's windows ([advanced-usage.md](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)). Users with several Chrome profiles cannot pick one, and that is a real limitation.

The secondary Chrome mode is a **dedicated agent profile**. Spawn `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` with an app-owned `--user-data-dir` and a debugging port. It runs alongside the user's main Chrome, keeps its cookies between runs, and needs no consent dialog ([advanced-usage.md](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)). Prefer `--remote-debugging-pipe` (Puppeteer `pipe: true`) so no TCP socket is listening. Google sign-in is the catch. Google has blocked sign-in since 2021 from browsers that "provide automation features" ([Google Developers Blog](https://developers.googleblog.com/2020/08/guidance-for-our-effort-to-block-less-secure-browser-and-apps.html)), and one Chromium vendor reports that an exposed debugging port alone can trigger the block ([TeamDev](https://teamdev.com/dotnetbrowser/docs/guides/troubleshoot/common-issues/)). The workaround is to sign in to the dedicated profile once with no automation attached. It is best-effort, because Google's detection is undocumented. This is the main reason auto-connect is the better default for Chrome: Google logins already exist in the real profile.

## Zen requires a relaunch, and only WebDriver BiDi is available

Zen installs at `/Applications/Zen.app/Contents/MacOS/zen` and tracks the Firefox **release** channel closely. Zen 1.23.4b on Firefox 158.0.1 shipped on 20 October 2026, five days after the previous build ([Releasebot](https://releasebot.io/updates/zen-browser)). Gecko's protocol situation is simple: **CDP was disabled by default in Firefox 129 and removed in 141**, so WebDriver BiDi is the only protocol ([fxdx.dev](https://fxdx.dev/?p=289); [Firefox Remote Prefs](https://firefox-source-docs.mozilla.org/_sources/remote/Prefs.md.txt)). The Remote Agent's listener **starts only when the browser is launched with `--remote-debugging-port`**. It accepts only loopback hosts and requests with no `Origin` header ([Firefox Remote Agent Security](https://firefox-source-docs.mozilla.org/remote/Security.html)). The endpoint is `ws://127.0.0.1:PORT/session`. With port 0, the actual port appears on stderr as `WebDriver BiDi listening on ws://127.0.0.1:N` ([MDN](https://developer.mozilla.org/en-US/docs/Web/WebDriver/How_to/Create_BiDi_connection)). Unlike CDP, there is no `/json` discovery. A community `zen-mcp` server already drives Zen this way, which is good evidence that Zen has not stripped the Remote Agent ([MacMyths](https://macmyths.com/how-to-use-zen-browser-with-an-mcp-server/)).

The relaunch requirement makes Zen's attach story the inverse of Chrome's. No consent toggle exists. To use the user's real profile with its logins, the server detects a running Zen, asks the user to quit it, and relaunches the binary as `zen --profile "<abs path>" --remote-debugging-port 0`. Firefox needs an unlocked profile, a stale `.parentlock` can survive a crash ([Mozilla Support](https://support.mozilla.org/en-US/kb/firefox-already-running-not-responding)), and running the binary again while Zen is open "may only open a window and exit" unless you pass a separate `--profile` ([fxdx.dev](https://fxdx.dev/?p=289)). That last behavior is what makes a **dedicated Zen agent profile** workable: it can run as a second instance beside the user's normal Zen. The profile root on macOS is **unverified**. By Firefox convention it is probably `~/Library/Application Support/zen/` with a `profiles.ini`, but Zen's docs give no paths and its Linux layout has moved between versions ([noctalia #1839](https://github.com/noctalia-dev/noctalia/issues/1839)). Resolve it at runtime from `profiles.ini`, preferring the `[Install…] Default` entry, and let the user confirm it via `about:profiles`.

Three Gecko pitfalls shape the implementation. First, the BiDi server effectively allows **one active session**. A client that disconnects without `session.end` leaves a zombie, and new connections then fail with "Maximum number of active sessions" until Zen restarts ([MacMyths](https://macmyths.com/how-to-use-zen-browser-with-an-mcp-server/)). Always end the session on shutdown and on idle. Second, `remote.prefs.recommended` defaults to on and applies automation prefs at startup, such as disabling update checks and first-run UX ([Firefox Remote Prefs](https://firefox-source-docs.mozilla.org/_sources/remote/Prefs.md.txt)). On a real profile, set it to `false` in `user.js`. It is unverified whether these prefs persist. Third, **avoid Marionette**. Mozilla's own firefox-devtools-mcp needs both `--marionette` and `--remote-debugging-port` for its connect-existing mode, and Marionette sets `navigator.webdriver = true`, which can trip Cloudflare and Akamai bot detection ([firefox-devtools-mcp README](https://raw.githubusercontent.com/mozilla/firefox-devtools-mcp/main/README.md)). Whether BiDi alone also sets that flag is uncertain and should be tested on day one.

Puppeteer is the right Node library for Zen. It has had official Firefox support over BiDi since Firefox 129 ([Mozilla Hacks](https://hacks.mozilla.org/2024/08/puppeteer-support-for-firefox/)). `puppeteer.connect({browserWSEndpoint: 'ws://127.0.0.1:N/session', protocol: 'webDriverBiDi'})` attaches after a `session.status` probe. You must pass the full `/session` URL, and `browser.close()` sends `browser.close`, which **quits Zen** ([puppeteer-core BrowserConnector.ts](https://app.unpkg.com/puppeteer-core@25.4.0/files/src/bidi/BrowserConnector.ts)). The BiDi support table sets your ceiling. Locators, `$`/`$$`, file upload, cookies and request interception work. **`accessibility.snapshot()` and ARIA selectors do not**, and screenshots and viewport control are partial ([pptr.dev](https://pptr.dev/webdriver-bidi)). Launch Zen yourself and then connect. Do not use `puppeteer.launch({userDataDir})` against the real profile, because it may write automation prefs there. Playwright is not an option for Zen: it drives its own patched Firefox builds ([microsoft/playwright#5872](https://github.com/microsoft/playwright/issues/5872)), and its stock-Firefox BiDi support is still experimental.

| | Google Chrome | Zen (Gecko) |
|---|---|---|
| Protocol | CDP | WebDriver BiDi only (CDP removed in Fx 141) |
| Real-profile attach | Chrome 144+ toggle at `chrome://inspect`, Allow dialog per connection | Quit Zen, relaunch with `--profile … --remote-debugging-port 0` |
| Endpoint discovery | `~/Library/Application Support/Google/Chrome/DevToolsActivePort` (port + path) | stderr line `WebDriver BiDi listening on ws://127.0.0.1:N`, append `/session` |
| Dedicated agent profile | `--user-data-dir=<app dir>` + pipe, runs alongside main Chrome | Separate `--profile` dir, runs alongside main Zen |
| Library | puppeteer-core 25.x (`browserWSEndpoint`) | puppeteer-core 25.x (`protocol:'webDriverBiDi'`) |
| Built-in a11y snapshot | Yes (CDP) | No, so inject your own |
| Key gotchas | Multiple profiles: default only; Google sign-in block in agent profile | One session at a time; zombie sessions; `remote.prefs.recommended`; Marionette fingerprint |

## Existing servers cover each browser separately, but none covers both safely

Off-the-shelf options already work for each browser. **chrome-devtools-mcp `--autoConnect`** handles Chrome's real profile today. It sends usage statistics and performance-trace URLs to Google by default; turn them off with `--no-usage-statistics` and `--no-performance-crux` ([DevTools auto-connect docs](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect)). **@mozilla/firefox-devtools-mcp** can probably be pointed at Zen via `--firefox-path`, but that is untested. Its attach mode requires Marionette, and it is unclear whether `--profile-path` uses the profile in place ([firefox-devtools-mcp README](https://raw.githubusercontent.com/mozilla/firefox-devtools-mcp/main/README.md)). **zen-mcp** is a small community project. Running two of these side by side gives Claude two different tool vocabularies, two ref formats, and no shared safety layer. That is the argument for building one server. Use the existing projects as references for design and wire behavior.

The architecture follows from the sections above. A **BrowserManager** owns one Puppeteer `Browser` per target (`chrome`, `zen`), handles attach, launch and reconnect, and always disconnects rather than closing. A **snapshot module** runs one injected script in either browser. Because Puppeteer's a11y snapshot is unavailable over BiDi, an injected DOM walker is the only representation that behaves the same in both, and it lets you apply hidden-text stripping and sensitive-field redaction in one place. For Chrome only, you could later swap in CDP's `Accessibility.getFullAXTree` or Playwright's `ariaSnapshot({mode:'ai'})` with `noDefaults: true`, which keeps Playwright's default overrides off the user's daily browser ([npm playwright-core](https://www.npmjs.com/package/playwright-core)). That would buy semantic fidelity at the cost of two code paths. A **policy engine** sits between every tool handler and the browser. The MCP layer itself should target the **TypeScript SDK v2** (`@modelcontextprotocol/server` 2.4.0, zod v4, `registerTool(name, {inputSchema: z.object(…), annotations}, handler)`, stdio transport). v2 became the stable line on 2026-07-27, and `@modelcontextprotocol/sdk` 1.x moved to maintenance ([@modelcontextprotocol/server](https://www.npmjs.com/package/@modelcontextprotocol/server); [@modelcontextprotocol/sdk](https://www.npmjs.com/package/@modelcontextprotocol/sdk)). Register the server at user scope with `claude mcp add --scope user browser -- node /path/to/server.js` ([mcpbundles guide](https://docs.mcpbundles.com/blog/claude-code-mcp-tools)).

## Compact refs and targeted reads keep pages under Claude Code's 10k-token warning

The surveyed servers have converged on one representation. The page goes to the model as an **indented text tree of role, accessible name and state**. Interactable nodes carry opaque handles, `[ref=e12]` in Playwright and `uid=3_17` in chrome-devtools-mcp, and action tools take that handle. Playwright caches each ref on the DOM element and reuses it while role and name are unchanged. A ref resolves only against the latest snapshot and only if `element.isConnected` ([npm playwright-core](https://www.npmjs.com/package/playwright-core)). chrome-devtools-mcp keys its uids on `loaderId + backendNodeId`, so they are stable for the life of a document and change after navigation ([npm chrome-devtools-mcp](https://www.npmjs.com/package/chrome-devtools-mcp)). Your injected script should copy this: a global counter, a per-element cache keyed on role+name, a last-snapshot lookup table, a connectedness check, and a clear "stale ref, re-snapshot" error. Prefix refs with the browser and tab (`z3:e12`) so a ref from Zen can never land in Chrome. Playwright's recent rename of `ref` to `target`, which accepts "a ref or a unique selector," suggests a selector fallback helps the model recover from stale refs ([@playwright/mcp README](https://www.npmjs.com/package/@playwright/mcp)).

Token budget is the binding constraint. Claude Code warns when an MCP tool result exceeds **10,000 tokens** and caps output at a `MAX_MCP_OUTPUT_TOKENS` default of **25,000** ([mcpbundles guide](https://docs.mcpbundles.com/blog/claude-code-mcp-tools), secondary source). The servers use six techniques to stay inside it, and a productivity server should use all of them. **Filter to interactive nodes by default**, and drop layout-only wrappers and StaticText that repeats the parent's name. **Scope** reads by ref or selector, and add depth limits. **Hard-cap** output, and say so explicitly when it is truncated: Firefox's MCP caps at 100 lines and Claude in Chrome's `read_page` at 50,000 characters ([firefox-devtools-mcp](https://www.npmjs.com/package/@mozilla/firefox-devtools-mcp); [Claude in Chrome](https://support.claude.com)). **Offer a `find` tool** that searches the tree by text or regex and returns matches with context. Playwright says this is "cheaper than capturing the whole snapshot" ([@playwright/mcp README](https://www.npmjs.com/package/@playwright/mcp)). **Write bulk output to a file** and return the path plus a preview. Mozilla notes Claude Code's `Read` tool can then page through it "without impacting context size" ([firefox-devtools-mcp](https://www.npmjs.com/package/@mozilla/firefox-devtools-mcp)). **Make the post-action snapshot opt-in.** chrome-devtools-mcp's own skill advises `includeSnapshot: false` unless updated state is needed ([npm chrome-devtools-mcp](https://www.npmjs.com/package/chrome-devtools-mcp)). Playwright has dropped its "incremental" diff mode in favor of full/none plus `find`. That suggests targeted reads beat diffs, though no changelog confirms the reasoning. For reading content rather than acting on it, a separate `read_text` tool with a character cap (Firefox uses 20,000) is cheaper than any tree.

A focused tool surface of about 18 tools covers everyday productivity work. Claude Code defers MCP tool schemas through Tool Search by default, so the cost of a moderate tool count is low ([mcpbundles guide](https://docs.mcpbundles.com/blog/claude-code-mcp-tools)).

| Group | Tools | Notes |
|---|---|---|
| Session | `browsers_status`, `connect` | Reports which browser is attached, the profile mode and the session age |
| Tabs | `tabs_list`, `tab_new`, `tab_close`, `tab_select` | Every page tool takes explicit `browser` + `tabId`, as chrome-devtools-mcp and Claude in Chrome require |
| Read (readOnlyHint) | `snapshot`, `find`, `read_text`, `screenshot` | `filter`, `ref` scope, `max_chars`, `save_to`; screenshot `scale` |
| Act (destructiveHint) | `navigate`, `click`, `type`, `fill_form`, `select_option`, `press_key`, `scroll`, `upload_file`, `handle_dialog`, `wait_for` | Each takes `target` and a required one-line `intent`, used for audit and confirmation |
| Compose | `batch` | Runs actions in order and stops on the first error. Each item runs its own policy check |
| Off by default | `evaluate` | Arbitrary JS bypasses every control below. Expose it only behind a config flag and always gate it |

Two conventions from Claude in Chrome and Playwright are worth copying. Mutating tools carry a human-readable description field, Claude in Chrome's `action_summary` and Playwright's `element`, which feeds permission prompts and logs. And screenshots are explicitly not the action channel: Playwright's tool description says "You can't perform actions based on the screenshot" ([@playwright/mcp README](https://www.npmjs.com/package/@playwright/mcp)). Treat the model's description as a label only. As the next section explains, the confirmation shown to the user must come from the live DOM.

## Prompt injection still succeeds 1–2% of the time, so the server must say no

Every major browser-agent vendor has published working indirect prompt injections against logged-in browsers. Brave's Comet proof of concept hid instructions behind a Reddit spoiler tag. The agent then read the user's Perplexity email address, requested a login OTP via a trailing-dot domain (`perplexity.ai.`), read the OTP from Gmail, and posted both back to Reddit, giving full account takeover ([Brave](https://brave.com/blog/comet-prompt-injection/)). Later Brave work showed that faint text in images gets through via screenshots, and that merely *navigating* to a page can be enough ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). OpenAI described an injected email that made Atlas send a resignation letter to the user's CEO ([OpenAI](https://openai.com/fr-CA/index/hardening-atlas-against-prompt-injection/)). The best published defenses are model training plus classifiers on all untrusted content. They cut an adaptive attacker's success against Claude Opus 4.5 from **8.0% to 1.4%**. Anthropic itself says "no browser agent is immune" and that 1% is "meaningful risk" ([Anthropic](https://www.anthropic.com/news/prompt-injection-defenses)). A local MCP server gets none of those classifiers for free. Its contribution is deterministic controls that hold even when the model is fooled.

**Scope and data flow.** Keep a per-task origin allowlist in the server, seeded from the user's request. Navigating outside it requires confirmation. Normalize hosts before comparing: lowercase, strip the trailing dot, decode punycode, and compare on eTLD+1. The Comet chain needed three cross-site hops and a trailing-dot domain. Also flag the exfiltration shape behind every documented attack: **reading a sensitive origin (mail, account pages) and then typing into a different origin** should require confirmation. Add a step cap and a per-minute action rate limit per task. OpenAI's automated attacker found injections that steer agents through "dozens or hundreds of steps" ([OpenAI](https://openai.com/fr-CA/index/hardening-atlas-against-prompt-injection/)).

**Content hygiene.** Wrap every snapshot and text result in delimiters such as `<untrusted_web_content origin="…">`, and escape any closing tag that appears in page text. The snapshot walker should skip `display:none`, zero-size, off-screen, `aria-hidden` and near-zero-contrast text, and report "N hidden elements omitted" rather than dropping them silently. This targets the white-on-white and HTML-comment tricks Brave documented. It is a cheap partial measure, not a boundary, and screenshots remain an injection channel.

**Credentials and money are off-limits.** Claude in Chrome prohibits inputting sensitive data, stock trading and captcha bypass, and asks before visiting financial sites ([Claude Help Center](https://support.claude.com/en/articles/12902428-using-claude-in-chrome-safely)). The MCP spec forbids collecting passwords or payment credentials via form elicitation ([MCP Elicitation spec](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)). Enforce the same rules structurally. Refuse `type`/`fill` into `input[type=password]`, fields whose `autocomplete` is `current-password`, `one-time-code` or `cc-*`, fields whose names or labels match OTP/CVV/card/IBAN/SSN patterns, and anything inside a payment-processor iframe. Redact those values from snapshots too. The autocomplete token list comes from prior knowledge and should be checked against the HTML spec. Ship an editable domain policy that **blocks** password-manager vaults and `chrome://`/`about:` pages, and makes banking, payment, government, health, identity-provider security pages and mail-forwarding settings **read-only plus confirm-on-navigate**. OTPs count as credentials: the Comet exploit stole one.

**Human confirmation the model cannot forge.** Classify each action in code against the *live* element, re-resolved right before execution. Mark as HIGH: submits and buttons whose name matches send/pay/buy/delete/post/share/authorize, uploads, downloads, dialog acceptance, off-scope navigation and `evaluate`. Show the user the real button text, page origin and field values, not the model's `intent`. The channel is **MCP elicitation**. A form-mode `elicitation/create` with a boolean approve field must offer decline and cancel, and the client must name the requesting server ([MCP Elicitation spec](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)). Claude Code reportedly added elicitation support in v2.1.76 in March 2026 ([Havoptic](https://www.havoptic.com/r/claude-code-2.1.76), secondary source). Check `clientCapabilities.elicitation` at initialize. If it is absent, fall back to a native `osascript` dialog from the server process. Never return a confirmation token in the tool result, because an injected model can simply pass it back. Also set `readOnlyHint`/`destructiveHint` annotations so Claude Code can apply its own prompts. The spec calls annotations untrusted hints ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/index.md)), so they supplement the gate and never replace it.

**Local attack surface.** An open debugging port lets any same-user process dump decrypted cookies. That is MITRE T1539, and why Chrome 136 changed course ([SpecterOps](https://specterops.io/blog/2020/12/17/hands-in-the-cookie-jar-dumping-cookies-with-chromiums-remote-debugger-port/); [Chrome for Developers](https://developer.chrome.com/blog/remote-debugging-port)). Use pipe transport for launched Chrome. Bind Zen to `127.0.0.1` on a random port. Never pass `--remote-allow-origins=*`. Close the session and let the port go when idle. Use stdio for MCP, never an unauthenticated HTTP listener. Expect EDR tools such as Elastic's "Potential Cookies Theft via Browser Debugging" rule to flag debugging launches ([Elastic](https://www.elastic.co/guide/en/security/current/potential-cookies-theft-via-browser-debugging.html)). Finally, keep an append-only JSONL **audit log** with `0600` permissions. For each action, record the tool, the redacted arguments, the resolved element, the origin before and after, the risk class and the confirmation outcome. Expose a `recent_actions` tool so the user can see what happened.

## Conclusion

The "drive my real browser" request comes down to a consent problem that each vendor solved differently. Google built a deliberate, user-visible handshake into Chrome 144, so the safest Chrome path is also the easiest. Gecko has no equivalent, so Zen's real-profile mode means relaunching the user's daily browser with an open control port for the whole session. Expect to recommend a **dedicated Zen agent profile as the default** and the real profile as an explicit opt-in, while Chrome can default to auto-connect. Build Zen support first and test it hardest, because it carries the most unknowns: the profile path, `navigator.webdriver` under BiDi-only, and single-session recovery. A day-one test plan should check those three and whether Chrome's Allow dialog survives restarts.

The bigger point is that the safety layer is the product. Protocol plumbing is now mostly commodity, since Puppeteer speaks both protocols and the snapshot and ref design is settled. What the existing servers lack is the in-code policy engine: origin scope, the sensitive-field firewall, live-DOM confirmation over elicitation, and the audit trail. With a 1–2% residual injection rate and the user's email, calendar and accounts reachable, the controls the server enforces matter more than anything in the prompt.
