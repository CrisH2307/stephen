# GitHub agentic workflows: the GH-AWTrace paper and Stephen

Status: research note, 2026-11-25. Docs only. Fixes for #329 and #330 go to those PRs through the top lead.

## 1. The paper in short

GH-AWTrace: A Large-Scale Dataset of GitHub Agentic Workflow Execution Logs (arXiv 2611.06866, cs.SE, 4 Nov 2026).
Authors: Khelifi, Li, Ouni, Sayagh, Saied.

- **What it is:** a dataset of GitHub Agentic Workflows (gh-aw, the GitHub tool that compiles markdown into Actions
  files). 25,014 workflows in 5,051 repositories, 4.1 million run records (Aug 2025 to Sep 2026), 562,877 non-empty
  log archives from the last 90 days.
- **How it was built:** GitHub code search for the "automatically generated by gh-aw" header, then the workflow runs API.
  Logs only exist for 90 days, so only that window was downloaded. Logs are partial (821,672 runs have no archive,
  1,070,338 archives are empty).
- **Failures:** 31.7% of non-empty archives belong to runs that ended in failure. The paper does not say why.
- **Triggers seen (share of logs):** schedule 44.9%, `pull_request_target` 13.1%, `pull_request` 10.9%,
  `issue_comment` 10.4%, `workflow_dispatch` 8.2%, `issues` 4.8%. The paper does not call any of them unsafe.
- **Tools:** none. It releases data and one Python example script. No checker or linter.
- **License:** the paper is under the arXiv non-exclusive license. The dataset license is not stated on the pages
  read. Check the dataset card: https://huggingface.co/datasets/jaykay9999/GHAWTrace (not yet checked, needs a
  Hugging Face login to be sure).
- **Caveat:** this summary comes from the abstract page and the HTML version. The PDF was binary and could not be
  read as text. Appendices were not seen.

**Important:** the paper is a dataset paper. It does **not** measure prompt injection, over-broad permissions,
secret exposure or unpinned actions. It only points to two other papers that do (arXiv 2605.07135, agentic workflow
injection in GitHub Actions, and arXiv 2606.09935, GitInject). Those two are the better source for the security
patterns below. We have not read them yet. The patterns in section 3 are the well known ones for agentic workflows
on public repos, checked against our files.

## 2. What the paper means for us

- Its trigger numbers show that `pull_request_target` and `issue_comment` are common for agents. Both run with
  repo secrets and take text from outsiders, so they are the risky pair. Stephen uses `pull_request_target`
  (#329) and `issues` (#330).
- 31.7% failed runs is a reminder to budget for failure: our `report` job in #330 already posts a fixed message
  on failure. Good.
- The dataset is for studying many repos. Stephen has two workflows. See section 5.

### #330 incident auto-wake: `.github/workflows/incident.yml` (branch `ci/incident-autowake`)

1. **Prompt injection (the main risk). Mostly handled.** The issue text goes in through `env` (line 50), is cut down
   to lines `stephen report` writes (line 52), then put in the prompt (line 117) as data. The agent has no shell,
   no web, only `Read` of src, docs and test (lines 95 to 106). Output is a fixed JSON schema (line 107) and is
   checked again before posting (line 183). The posted text goes inside a code block with no links.
   Remaining risk: the whole defense is the `parse` filter. If it lets one free-text field through, injection is
   possible. **Fix:** add a fuzz test for `parseIncidentIssue` (random text, long lines, unicode, markdown, `@name`,
   URLs, "ignore previous instructions") and assert that no output field holds a space-separated sentence.
2. **Allow-list by author id (lines 26 to 29). Good, but weaker than it looks.** `stephen report` files the issues
   from testers' Macs through Cris's account, so the author is always Cris and the body is still tester text.
   The strict line filter is the real control, not the id check. Say this in ADR-017 so nobody trusts the id check alone.
3. **`allowed_non_write_users` (line 91). Remove it.** It tells the action to skip its own write-access check for
   the issue author. Cris already has write access, so it is not needed. Leaving it on means that if the `if:`
   on line 26 is ever loosened, the second guard is already off. **Fix:** delete the line.
4. **`edited` trigger with a 10 minute sleep (lines 13 and 38).** Each edit starts a new job that holds a runner
   10 minutes. Only Cris-authored issues pass the `if:`, so it is a cost issue, not a security one. Keep. Fine.
5. **Secret exposure. Good.** The token is only in an environment limited to `main` (line 64). Tools that could read
   it are denied (lines 96 to 98: `/proc`, `~/.claude`, `_temp`, `_actions`, `.git`). `persist-credentials: false`
   on every checkout. No `Bash`.
   Remaining: the Claude action installs the Claude CLI from npm at run time, which is not pinned by us. **Fix
   (low):** set the action input for the CLI version if it has one, or accept the risk and note it in ADR-017.
6. **Permissions. Good.** `permissions: {}` at top (line 15), narrow per job. `investigate` has `issues: read` only.
   Check that the action does not need `issues: write` to run (it may try to make a tracking comment). If the
   first run fails on that, do not widen it: set `track_progress: false` if the action has it.
7. **Pinned actions. Good.** Six uses, all with hashes (lines 39, 42, 73, 85, 133, 157, 160, 166, 207, 211).
8. **Auto fix path (lines 126 to 241). Good design.** The job with the token only makes a patch. The job that
   pushes has no token for Claude and checks the patch paths (lines 215 to 229). Two gaps:
   - The check allows `test/*`. A patch can add `test/setup.ts` or edit a vitest hook that runs on every test run.
     It runs only in PR CI (no secrets) after review, so risk is low. **Fix:** also refuse `test/global-setup.ts`
     and any file named `*.config.*` or `setup*`, and require a human review (the PR title already has `[DEV REVIEW]`).
   - The PR title `[DEV REVIEW]` is what #329 uses to decide if a Cris approval is needed. See #329 finding 1.
9. **Cost and abuse.** `--max-turns 40` caps turns, but there is no spend cap. It is Cris's own token. **Fix:** add a
   daily run cap (for example, skip if more than N `incident` runs today) and keep `AUTO_FIX` off until the
   parse fuzz test exists.
10. **Cache.** `setup-node` with `cache: npm` (lines 42 to 45, 160 to 163) in a job near a secret. The Claude token job
    does not use it (good: `investigate` has no `setup-node`). Keep it that way.

### #329 merge-ready auto-merge: `.github/workflows/merge-qa.yml` (branch `chore/merge-to-qa`)

1. **`[DEV REVIEW]` is decided by the PR title (`scripts/merge-to-qa.sh` line 30). High.** The PR author controls the
   title. A PR that edits `src/safety/` and has no tag in the title skips the Cris approval check. AGENTS.md says
   changes to `src/safety/`, `helper/AppConfirm.swift`, the memory, timer and job write paths and the app.sock
   protocol need review. **Fix:** decide from the changed files, not the title. Read `gh pr view --json files` and
   require the approval comment when any path matches a protected list. Keep the title check as an extra, never as the
   only gate. Protected list: `src/safety/`, `helper/AppConfirm.swift`, `.github/`, `scripts/merge-to-qa.sh`,
   `scripts/incident-bot.mjs`, `src/telemetry/incident-bot.ts`, the memory, timer and job write paths, the app.sock
   protocol files.
2. **A PR can change the checks it is judged by. High.** `ci.yml` runs from the PR head on `pull_request`. A PR that
   edits `ci.yml` can make jobs named `linux` and `macos` pass without running tests. The script only checks
   job names (lines 25 to 28). **Fix:** treat any change under `.github/` as protected (finding 1), and also match the
   check by workflow name: require `workflowName == "ci"` as well as the job name.
3. **The label is not tied to who added it (line 11 and script line 24). Medium.** `pull_request_target` runs for
   whoever has triage or write access. All our lanes act as Cris, so this cannot split lanes, but it also does not
   stop a later collaborator. **Fix:** in the `if:` for the `labeled` path, add
   `github.event.sender.login == 'CrisH2307'`. For the `workflow_run` path the label is read later, so also ignore it if
   the label was added by anyone else (check the PR timeline events in the script, or drop the `workflow_run` path and
   rely on re-labeling).
4. **Fork PRs (line 58 filter on `base.ref`). Medium.** Nothing refuses a PR from a fork. A fork PR gets a read-only
   `pull_request` run, and its `workflow_run.pull_requests` list is empty, so the `workflow_run` path does not find
   it, but the `labeled` path will, if Cris labels it. **Fix:** in the script refuse when `isCrossRepository` is true.
5. **Workflow file and script come from different branches (header lines 10 to 14).** `pull_request_target` uses the
   workflow file from `qa`, and the script is read from `main`. A PR that changes `merge-qa.yml` and gets merged into
   `qa` changes what runs for all later PRs, before `main` sees it. Covered by finding 1 if `.github/` is protected.
   Also add `.github/CODEOWNERS` with `* @CrisH2307` for `.github/` and `scripts/merge-to-qa.sh` (no new action, free).
6. **Approval binds to the commit (script lines 30 to 35). Good.** `--match-head-commit` (line 39) stops a push
   after the check. One gap: the comment check is `startsWith` and `includes(short)` of 7 characters, from author
   `CrisH2307`. Since every lane posts as Cris, a lane can approve its own PR. This is the known limit from AGENTS.md
   and `docs/` (the review lane is a separate session but the same account). **Fix (optional):** require 12 characters of the SHA, and
   an `independent-reviewer` marker line that the author lane never writes.
7. **Pinned actions and permissions. Good.** One action, pinned (line 40). `permissions: {}` at top, narrow on the job.
   `persist-credentials: false`. Event text goes through `env`, never into `run:`.
8. **GITHUB_TOKEN merges do not start new runs (header lines 5 to 6).** So the CI on `qa` and the `ci-failure` issue
   will not fire after an auto-merge. Not a security issue. **Fix (ops):** a nightly `schedule` run of `ci` on `qa`, or
   accept that Cris sees it at the next PR.

## 4. Checks we can run in CI (free, one at a time, each needs Cris's OK first)

None of these is added yet. Each is a new tool, so Cris decides.

1. **`actionlint`** (MIT, free). Finds expression mistakes and unsafe `${{ }}` use in `run:`. Install by pinned
   release binary with a checksum, or run through `go run` pinned to a version. A new dependency: ask first.
2. **`zizmor`** (MIT, free, static analyzer for GitHub Actions). Flags template injection, excessive permissions,
   unpinned actions, `pull_request_target` misuse, cache poisoning. This is the best fit for what we worry about.
   It would have found #329 findings 3 and 5 only partly (it does not know our script), but it checks the pattern list
   above automatically. Run as a pinned binary in a read-only job with no secrets.
3. **Our own tiny test, no new tool.** A vitest test in `test/checks/` that reads every file in `.github/workflows/`
   and asserts: every `uses:` has a 40 character hash; no `${{ github.event.` text inside a `run:` block; top-level
   `permissions:` exists; no `pull_request_target` job checks out `github.event.pull_request.head`. `test/checks/`
   already holds a similar test for `merge-to-qa.sh`. This costs nothing and needs no approval beyond the PR.
4. **GitHub's own free settings:** secret scanning with push protection, Dependabot alerts, and "require approval for
   all outside collaborators" for workflow runs. Settings only, no code.

Recommended order: (3) now, then (2) with Cris's OK, then (1).

## 5. Does using the dataset make sense?

No, not for now.

- It is about gh-aw workflows in other repos. Stephen does not use gh-aw.
- It has no labels for attacks or for secure and unsafe workflows, so it cannot train or tune a checker for us.
- It is large (logs 56 GB for the window) and the license is not clear. We should not copy logs into this public repo.
- The paper has no security result to reuse. The two papers it cites are more useful.

What is worth doing: read arXiv 2605.07135 and 2606.09935 for their injection patterns, add them as test cases for
`parseIncidentIssue`, and check the Hugging Face dataset card for the license before anyone touches the data. For the
professor, a fair summary is: the paper is a good data source for studying agent behavior at scale, but it does not
give us a security checker, so we use zizmor and our own tests.
